# Dance v0.2.3

Fixes concurrent login-limit bypasses, tightens production session-key validation and refreshes dependencies. No new application features or database-format changes.

## Fixes

- Reserve login attempts before password verification. Concurrent requests can no longer all pass the five-attempt check before failures are recorded.
- Bound retained login-limiter state to 4,096 clients without evicting active blocks.
- Require an explicit session-signing key of at least 32 bytes outside development mode, including over HTTP. Ephemeral development keys remain available with `DANCE_DEVELOPMENT_MODE=true`.
- Update container publication smoke tests to supply a random production signing key.
- Exclude local environment files, CA keys/configuration, databases and generated release archives from Docker build contexts.
- Update deprecated archive configuration fields for current GoReleaser.

## Dependencies and toolchain

- Go 1.27.2 for the module and Docker builders.
- Refresh Go dependencies to current releases within their existing module major versions, including httpsnoop 1.1.0, chi 5.5.0, x/crypto 0.58.0 and SQLite 1.60.1.
- Refresh transitive HTTP/2, Unicode, JOSE, gRPC, pgx and OpenTelemetry dependencies to address advisories reported by the initial vulnerability scan.
- Embedded step-ca remains on the current certificates 0.30.2 / nosql 0.8.0 modules; the application/CA storage boundary is unchanged.

## Release targets and Actions costs

Darwin/macOS release targets were removed to save GitHub Actions costs. Release configuration on `main` now builds Linux AMD64 binaries on `ubuntu-24.04` and Linux ARM64 binaries on `ubuntu-24.04-arm`, both natively. Each Linux runner cross-compiles only the matching Windows architecture. No Darwin or Windows runners are used; macOS/iOS certificate-enrollment support is unchanged.

The initial v0.2.3 publication finished before these runner/target changes. Its Darwin downloads and their checksum entries were subsequently removed; the published tag was not rewritten. Native Linux binary packaging applies to future release tags. The original completed build's Actions usage cannot be recovered.

## Upgrade

Production deployments must provide a cryptographically random `DANCE_SESSION_KEY` of at least 32 bytes. Generate one once with `openssl rand -hex 32` and retain it in a protected environment file or secret store. Do not generate a new key on every service start. Replacing a key invalidates existing session cookies but does not alter administrator accounts or stored CA data.

Temporary local runs that previously relied on an implicit ephemeral key over HTTP must explicitly set `DANCE_DEVELOPMENT_MODE=true`. The documentation examples have been updated.

## Verification

Validated locally with Go 1.27.2 on Linux ARM64:

- `make check build`, the uncached race suite and session-verifier fuzz smoke test.
- govulncheck 1.9.0: zero reachable advisories and zero advisories in imported packages. The required x/crypto module retains GO-2026-5932 for its unused, unmaintained OpenPGP package; that package is not imported by Dance.
- actionlint 1.7.12 and GoReleaser 2.18.3 configuration validation.
- Docker context exclusion checks, non-root UID 65532, writable application state, login/health endpoints and graceful shutdown.
- Initial GoReleaser snapshot packaging covered Linux, macOS and Windows on AMD64 and ARM64, with all six archive checksums verified. Darwin distribution was subsequently removed as described above. Local packaging used `--parallelism 1` after an initial host OS-thread allocation failure.

Live CA deployments and external ACME clients were not exercised in this validation; existing embedded-CA unit tests passed.

The post-publication runner/target changes passed `make check`, actionlint, native-target selection regressions, both architecture-specific GoReleaser schema checks, and a reduced four-target snapshot. Native ARM64 Linux packaging plus Windows ARM64 cross-compilation was also exercised without publishing from a clean v0.2.3 worktree. The updated GitHub binary-packaging jobs apply from the next release tag; this does not change how the already-published v0.2.3 archives were originally built.
